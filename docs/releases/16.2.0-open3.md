# OpenAmigaGCC 16.2.0-open3

GCC 16.2 for AmigaOS 3.x (`m68k-amigaos`). Everything in open2 remains. Open3 makes the fixed toolchain self-identifying and removes the last external soft-float link workaround.

## New since open2

| Item | open2 | open3 |
| --- | --- | --- |
| Compiler identity | reported only bebbo's `16.2.0b` identity | `--version` reports `OpenAmigaGCC 16.2.0-open3` |
| `-m68020`, `-m68030` or `-m68040` without an FPU option | compiled soft-float code, but needed an external specs file to keep the linker off `libm881` | selects the `libm020` soft-float multilib by itself |
| Explicit `-m68881` or `-mhard-float` | selected the FPU multilib | still selects `libm020/libm881` |
| Reusing a retained source cache | a harmless patch-header rename could make the build reject an otherwise identical applied patch | the build accepts an equivalent historical patch revision by stable patch ID while still rejecting a changed diff |

The OpenNDK base-order correction and overridable varargs wrappers requested for open3 were already present in the pinned upstream source and are verified by the build; they are not duplicated as downstream patches. The blank `$VER:` result traced to literal scanner markers in OpenBench and OpenTata, not to GCC, and is fixed in those repositories.

## Checked with

- A complete offline build at `-j3` under `nice -n 19`, using only source inputs already retained on the build PC.
- The build's libnix recursion audit and compiler-default checks.
- `tests/repro/prove.sh`: every reproducer passes at its tested optimisation and CPU settings, including nested A6 calls, FPCR handling, 64-bit stack arguments, 68040/68060 soft float, calloc recursion and address-zero reads.
- `tests/cxx/lean-check.sh`: no exception, RTTI, static-constructor, guard or libstdc++ allocation dependency enters the lean object.
- Real links and linker maps: `-mcpu=68040` uses `libm020/libm.a` and no `libm881`; adding `-m68881` uses `libm020/libm881/libm.a`.

Amiga lab qualification and the shared-stove swap remain separate gated steps.

## Known

- The toolchain needs glibc 2.38 or later.
- The shared `libnix4.library` still does not link; normal static programs do not need it.
- Code written for GCC 6.5 may need updates for GCC 16's newer diagnostics.
